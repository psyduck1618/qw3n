Setup & maintenance

How this works

01 · Processes & ports

Every service on your Mac runs as a process and listens on a port — a number between 0 and 65535. Ports are doors; each service gets its own.

YOUR MAC
├── :8080   python3 server.py    serves this page + proxies to Ollama
├── :11434  ollama serve         runs the model
└── :9222   Chrome remote debug  browser automation

When you open http://127.0.0.1:8080 the browser connects to port 8080. The Python process that opened that port receives the request and sends back the HTML.

lsof -i :8080          # who owns the web server
lsof -i :11434         # who owns ollama
curl localhost:8080    # poke the server directly

02 · The glass

This interface is built from translucent layers. Each panel is a backdrop-filter that blurs and saturates whatever is behind it, plus a one-pixel specular highlight along its top edge.

.side, .main, .composer, .drawer
  background   rgba(255,255,255,.055)   ← thin white film
  backdrop     saturate(190%) blur(42px) ← the refraction
  box-shadow   inset 0 1px 0      ← the light on the edge
              0 24px 60px -28px #000     ← the shadow it casts

The four aurora blobs drifting behind everything are the light source. Glass is invisible without something to refract, so the background is never a flat colour.

backdrop-filter: blur(0)      → flat
backdrop-filter: blur(30px)   → frosted
backdrop-filter: blur(0)
                   + brightness(1.4)    → glass

03 · localhost vs LAN IP

  • 127.0.0.1 (localhost) — only your own machine can connect. Traffic never leaves the computer.
  • 192.168.x.x (LAN IP) — other devices on your WiFi can connect. Your router assigned this via DHCP.
LOCALHOST (127.0.0.1)
┌────────────────────────────┐
│  Browser ──Python──8080    │  traffic stays INSIDE the Mac
│  Browser ──Python──11434   │  never touches the network
└────────────────────────────┘

LAN (192.168.x.x)
┌────────────────────────────┐
│  Phone ──WiFi──▶ Router    │
│         Router ──▶ Mac     │  traffic goes THROUGH the network
└────────────────────────────┘

The server binds to 0.0.0.0, so the address the terminal printed works from your phone on the same WiFi. Tap Share at the bottom of the sidebar to copy it.

04 · Three ways in

The right door depends on who is connecting and from where.

┌─ LOCAL ───────────────────────────┐
│ 127.0.0.1:8080                    │  this Mac only
├─ HOME WI-FI ──────────────────────┤
│ 192.168.x.x:8080                  │  phone, tablet, laptop
├─ TAILSCALE  (--tunnel tailscale) ─┤
│ https://name.tailnet.ts.net       │  any device, VPN
└─ CLOUDFLARE (--tunnel cloudflare) ┐
   https://xxx.trycloudflare.com    │  any device, public URL
  • Tailscale — a private mesh VPN. Nothing is published to the internet; only devices on your tailnet can reach the port. Best default.
  • Cloudflare Tunnel — hands you a public HTTPS URL with no router changes and no open port. Use it when a device that can't run Tailscale needs access.
  • Router port forwarding — works, but it exposes the raw port to the entire internet over plain HTTP. Only sensible with the password gate, never without it.
# one flag, whichever tool is installed
./run.sh --tunnel

# or be explicit
python3 server.py --tunnel tailscale --funnel
python3 server.py --tunnel cloudflare

05 · The password gate

Any device that can reach the port can read and write your conversations, so the server requires a token. It is generated on first run, stored in data/.token, and printed in the terminal banner.

browser ──POST /api/login──▶ :8080  compares token
                           ◀──Set-Cookie: qwen_token=…──
browser ──GET /api/chats──▶ :8080  cookie sent automatically

The cookie is HttpOnly so page scripts can't read it, SameSite=Lax so other sites can't ride it, and marked Secure whenever the request arrived over HTTPS — which is every tunnelled case. Failed logins are rate limited per IP. Set your own with QWEN_TOKEN=… ./run.sh, or turn the gate off for a trusted LAN with --no-auth.

06 · CORS

Browsers refuse cross-origin fetches unless the server opts in. Calling :11434 straight from the page would require OLLAMA_ORIGINS=*. The proxy removes that whole class of problem: the browser only ever talks to :8080.

Browser ──▶ :8080 server.py ──▶ :11434 ollama
          same origin        server-to-server

07 · Request flow

1. You type a message
2. JS POSTs to /api/chat on this server
3. server.py builds an Ollama request and POSTs to :11434
4. Ollama loads model layers into RAM
5. Tokens stream back one at a time
6. server.py re-frames them as SSE  (data: {...})
7. JS appends each token to the bubble — you watch it type

Streaming is why the reply appears word by word instead of all at once. Same total time, better feel.

08 · Why it can be slow

The bottleneck is model inference, not the browser or your network.

  • Qwen3 8B has ~8.2B parameters
  • Q4_K_M quantizes weights to ~4 bits → ~5 GB
  • It has to fit in unified memory alongside everything else
  • First token is slow (load + prefill), then ~20–40 tok/s
  • Reaching it over the internet adds your round-trip time to every token
14B  Q4_K_M  ████████████░░░░░░░  9.0 GB
 8B  Q4_K_M  ███████░░░░░░░░░░░░  5.0 GB   ← good balance
1.7B Q4_K_M  ██░░░░░░░░░░░░░░░░░░  1.1 GB   ← fastest

09 · Useful commands

# start this server and open a browser
python3 server.py --open

# bind to localhost only (no LAN)
python3 server.py --host 127.0.0.1

# what models exist
curl http://127.0.0.1:11434/api/tags

# find your LAN address
ipconfig getifaddr en0

# where the data lives
data/chats/*.json     one file per conversation
data/.trash/*.json    deleted chats — move one back to restore it
data/.token           the password, mode 600

Conversations live as plain JSON in data/chats/. Deleting one moves the file to data/.trash/ rather than erasing it — drag it back to restore.
